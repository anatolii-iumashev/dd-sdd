# sdd-apply

Финализирует фичу: RFC уходит в архив, а фактическое решение становится частью актуальной документации в `docs/specs/`.

## Когда использовать

- Реализация по RFC завершена, критерии приёмки закрыты
- Пользователь говорит «завершаем», «фича готова», «закрой спеку», «перенеси в архив»

## Workflow

### Шаг 1. Найти RFC

- Если пользователь указал фичу — открыть `docs/rfc/<slug>.md`
- Если не указал — показать RFC со статусом `implementing` и спросить, какую завершаем

### Шаг 2. Проверить готовность к закрытию

- Пройтись по чеклисту «Критерии приемки» — все пункты должны быть отмечены
- Если что-то не закрыто — показать список и спросить: доделываем (назад к **sdd-implement**) или закрываем с оговорками (незакрытое зафиксировать в актуальных спеках как известное ограничение)

### Шаг 3. Перенести RFC в архив

- Обновить frontmatter RFC: `status: done`, добавить `completed: YYYY-MM-DD`
- Переместить файл: `docs/rfc/<slug>.md` → `docs/rfc/archive/<slug>.md`
- В git-репозитории использовать `git mv`

### Шаг 4. Интегрировать решение в docs/specs/

Сначала прочитать все статьи в `docs/specs/` (включая вложенные Markdown-файлы, если они есть). Найти документы, связанные с RFC по предметной области, компонентам, сущностям, API, пользовательским сценариям или уже зафиксированным решениям.

- Если связанные спеки есть — дополнить их итоговым состоянием фичи: новым поведением, принятыми решениями, отклонениями от RFC, ограничениями и ссылкой на архивный RFC, когда она полезна для трассировки. Не дублировать один и тот же материал в отдельной сводке.
- Сохранять структуру, терминологию и полезное содержимое существующих документов. Обновлять или заменять устаревшие утверждения, а не дописывать противоречащие им параллельные версии.
- Если связанные спеки отсутствуют — создать `docs/specs/<slug>.md` (и папку при необходимости) по формату ниже.
- Если RFC затрагивает несколько самостоятельных тем, обновить каждый релевантный документ; отдельную сводку создавать только для той части решения, которой ещё негде жить.

Формат нового документа:

```markdown
---
title: "<название фичи>"
status: done
completed: YYYY-MM-DD
rfc: ../rfc/archive/<slug>.md
---

# Spec: <название фичи>

## Что сделано

<краткая сводка: итоговое состояние, что реально работает>

## Ключевые решения

<решения, принятые в ходе реализации, включая отклонения от RFC>

## Отклонения от RFC

<что сделали иначе и почему; если не было — «не было»>

## Известные ограничения / дальнейшие шаги

<незакрытые критерии, техдолг, идеи на будущее; если нет — «нет»>
```

Документация должна описывать фактическое текущее состояние системы, а не план из RFC. Архивный RFC остаётся историей принятия решения; `docs/specs/` — единым актуальным источником знаний по предметной области.

### Шаг 5. Отчитаться

Показать пользователю:

- RFC в архиве: `docs/rfc/archive/<slug>.md`
- Созданные и обновлённые документы в `docs/specs/`
- Кратко: что интегрировано в каждый документ и почему не создавался отдельный файл, если использовались существующие спеки
- Предложить внести правки в актуальную документацию
