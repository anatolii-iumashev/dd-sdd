# DD-SDD Skill

**DD-SDD** = **D**iscovery–**D**elivery **S**pec-**D**riven **D**evelopment.

Навык для AI SDLC: полный цикл разработки с кодинг-агентом — от идеи до реализации и архивирования результатов, где единицей работы является не тикет, а спецификация.

## Установка

Через [skills.sh](https://www.skills.sh):

```bash
npx skills add https://github.com/anatolii-iumashev/dd-sdd --skill dd-sdd
```

Треки ставятся отдельно — они подключаются как навыки проекта и вызываются из `dd-sdd`:

```bash
npx skills add https://github.com/anatolii-iumashev/dd-sdd --skill dd-discovery
npx skills add https://github.com/anatolii-iumashev/dd-sdd --skill dd-delivery
```

Без `--skill` команда покажет список навыков репозитория и предложит выбрать.

После установки запустите `dd-sdd` — он проверит готовность проекта (см. «Перед стартом: preflight») и спросит, с какого трека начинать.

## Ключевые особенности

### 1. AI SDLC вместо «чата с ассистентом»

Разработка с агентом ведётся как управляемый жизненный цикл: у каждой фичи есть документ, статус, критерии приёмки и зафиксированный результат. Агент получает не переписку, а спеку.

### 2. Dual-track: Discovery + Delivery

Процесс построен на практиках dual-track agile — два параллельных трека вместо одной очереди задач:

- **Discovery** — исследуем проблему, проверяем гипотезы, формулируем решение и критерии приёмки. Результат трека — RFC.
- **Delivery** — реализуем то, что прошло discovery, и фиксируем фактический результат.

В delivery попадает только то, что готово в discovery. Обратная связь из delivery возвращается в discovery: неожиданные решения и отклонения от RFC становятся входом для следующих итераций.

### 3. Design docs на основе RFC

Спецификации пишутся в формате RFC (Request for Comments) — как design doc, который команда может ревьюить и комментировать до начала работы: проблема, цели, границы, решение, дорожная карта, критерии приёмки.

### 4. Компактная спецификация (~3000 слов)

RFC стараемся укладывать в ~3000 слов. Рабочий паттерн — две сессии:
- в одной пишем дизайн документ RFC — если надо, обсуждаем в команде или со стейкхолдерами;
- в чистой сессии передаем её кодинг-агенту.

Компактный RFC — это весь контекст исполнителя, без шума и истории переписки. Не уместились в ~3000 слов — повод декомпозировать фичу на несколько RFC.

Почему? Есть проблема контекстного окна:
- Заявленный context window: 1M+ токенов
- Usable context window: ~100–150K токенов — вырос лишь на ~20%
- После 200K токенов модель начинает «чудить»; после 350–500K — «make it worse»
- Lost in the middle syndrome: модель забывает середину, потом начало
- LLM плохо понимают, что важно → автоматическая компрессия контекста теряет критичное

Искусство маленьких шагов через RFC помогает обойти эту проблему и получить максимум из имеющихся ресурсов.

### 5. Декомпозиция: MECE и пирамида Минто

Design doc — не рассказ о задаче, а результат её разбиения. Две рамки, обе из практики McKinsey:

- **MECE** (Mutually Exclusive, Collectively Exhaustive — «взаимно исключающие, совместно исчерпывающие») отвечает за **разбиение**: части решения не пересекаются между собой и вместе покрывают задачу целиком. Разбиваем по одному основанию за раз (по слоям системы, по шагам сценария, по этапам жизненного цикла сущности), 3–7 пунктов на уровень.
- **Пирамида Минто** отвечает за **изложение**: сначала ответ — что делаем и почему, затем обоснование, затем детали. Вводные пишутся по SCQA: ситуация → осложнение → вопрос → ответ. Читатель понимает решение с первого экрана и может остановиться на любом уровне.

Практический эффект: «Составляющие», «Критерии приёмки» и «Дорожная карта» становятся тремя проекциями одной декомпозиции. Компонент без критерия приёмки, шаг дорожной карты, которого нет в составляющих, пересекающиеся пункты — это не огрехи оформления, а дыры в задаче, которые иначе всплыли бы уже в коде.

Отсюда же берётся и лимит объёма: если разбиение верхнего уровня даёт больше 5–7 блоков, каждый блок — готовый кандидат на отдельный RFC.

Ответственность за декомпозицию лежит на `dd-discovery`. Delivery её не чинит: кодинг-агент реализует ту структуру, которая ему передана.

## Две ключевые папки

- **`docs/rfc/`** — активные RFC: задачи, которые описаны и готовятся к реализации. `dd-discovery` пишет, `dd-delivery` читает.
- **`docs/specs/`** — актуальные спецификации: что реально сделано и как это работает сейчас. `dd-discovery` читает, `dd-delivery` обновляет.

Плюс `docs/rfc/archive/` — отработавшие RFC, история принятых решений.

- активные RFC: `docs/rfc/<slug>.md`
- архив RFC: `docs/rfc/archive/<slug>.md`
- актуальные спеки: `docs/specs/<slug>.md`

`<slug>` — короткое имя фичи в kebab-case, одинаковое на всех этапах цикла.

## Перед стартом: preflight

При запуске `dd-sdd` сначала проверяет, готов ли проект к циклу:

- есть ли контекст проекта — `AGENTS.md` (или `CLAUDE.md`);
- есть ли `docs/rfc/`, `docs/rfc/archive/`, `docs/specs/`;
- подключены ли треки — симлинки `dd-discovery` и `dd-delivery` в каталоге скиллов проекта.

Чего-то нет — скилл показывает, чего именно, и предлагает команды, чтобы завести (ничего не создаёт без подтверждения). Всё на месте — спрашивает, с чего начинаем: discovery и пишем RFC или delivery и реализуем уже существующий RFC.

## Цикл работы

### 1. `dd-discovery` — поставить задачу

Читает контекст проекта: актуальные спецификации в `docs/specs/`, активные RFC, при необходимости архив и код. Затем формулирует проблему и цели, раскладывает решение на непересекающиеся и полные части (MECE), излагает его по пирамиде Минто, задаёт критерии приёмки — и сохраняет design doc в `docs/rfc/<slug>.md`.

Задача ставится от текущего состояния системы и в её терминах, а не в вакууме.

Здесь же — основная ответственность за декомпозицию: структура RFC, которую получит delivery, определяется на этом шаге и дальше не переделывается.

### 2. `dd-delivery` — реализовать задачу

Берёт RFC из `docs/rfc/`, строит план по дорожной карте и:

- реализует фичу, отмечая закрытые критерии приёмки прямо в RFC;
- покрывает тестами поведение из критериев приёмки и прогоняет тесты проекта;
- дописывает в RFC раздел `## Тест инструкции` — пошаговую инструкцию проверки результата, где каждый шаг это `###`-заголовок со списком ссылок на тесты, страницы, эндпоинты и команды;
- обновляет `docs/specs/`, если фактическое поведение системы изменилось;
- переносит design doc в `docs/rfc/archive/` — когда всё готово или по команде в чате («перенеси в архив», «закрой спеку»).

Статус жизненного цикла хранится во frontmatter RFC: `draft → discovery → delivery → done`.

- `draft` — RFC пишется, ещё не готов к ревью;
- `discovery` — RFC готов, идёт ревью и согласование;
- `delivery` — RFC взят в работу, идёт реализация;
- `done` — реализовано, спеки обновлены, RFC уходит в архив.

## Когда использовать

Этот навык полезен, когда нужно:
- описать новую фичу перед разработкой;
- структурировать техническое задание или design doc;
- вести изменения по понятному процессу;
- держать документацию проекта в актуальном состоянии;
- сохранить историю решений и результатов для будущего.

## Коротко

Если у вас есть идея или изменение, которое хочется довести до релиза без хаоса — начните с RFC, затем реализуйте по нему, а после завершения зафиксируйте итог.
